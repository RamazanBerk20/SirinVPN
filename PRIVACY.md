# Privacy

Linux can remember administrator-approved VPN control for the invoking account
in a root-owned `/etc/polkit-1/rules.d/49-sirinvpn-user-<uid>.rules` file. It
contains only that account name and the allowed helper action IDs, never a
password. Permission applies to active local sessions and survives reboot;
installation, binary replacement and application launching still require
administrator authorization. Removing the rule revokes permission; Debian package
purge removes SirinVPN's generated rules. Disconnecting or removing a VPS profile
does not revoke this computer-level permission.

Linux automatic optimization uses a separate, temporary WireGuard peer to compare
configured transports without moving application traffic. The VPS grants one
120-second, memory-only measurement lease per authorized device. Probe peers use
`10.77.1.0/24` and may only echo to the private VPS address; management, peer access,
and forwarding are denied. Leases are excluded from backups and authorization
files and cease to authorize traffic on expiration, revocation, key rotation, or
server restart. Current connection health also checks the private management TCP
port and WireGuard receive/handshake progress; it does not contact public services.

For Linux sessions using automatic selection with the kill switch enabled, the
helper retains the current profile and management credentials in the root-only,
mode-0600 `/var/lib/sirinvpn/measurement-identity.json`. This lets optional
optimization continue after the desktop closes. Explicit Disconnect removes the
file. It is separate from preferences and exported backups. The current cooldown,
health evidence, and last switch reason live only in `/run/sirinvpn`, without an
activity timeline. Unsupported VPS versions continue with recovery-only selection.

Current client transport-quality probes send eight small ICMP echo requests to the
private VPS tunnel address at a bounded interval. Only the current comparison and
counter baseline are retained in volatile runtime state. No public speed-test
service, destination traffic capture, or measurement history is used. Optional
Wi-Fi automation stores the chosen server and an explicit list of trusted labels
and salted platform network fingerprints. It does not store raw network IDs,
SSIDs, BSSIDs, discovered-network history, or network-entry times. The list is user
configuration; discovery alone does not add entries.

While Wi-Fi settings are visible, the desktop reads saved OS Wi-Fi names locally
to identify the current connection and explicitly trusted entries. Linux resolves
the saved NetworkManager profile's SSID; Windows uses its saved network name.
These display names remain in memory only: they are not logged, stored in
SirinVPN state, included in diagnostics/backups, or transmitted to the VPS or
any other service. User-entered friendly labels remain explicit local settings.

The desktop remembers explicitly verified SSH host-key fingerprints in a
private local `ssh-host-keys.json` file, scoped to the host address and SSH port.
It stores only the current key per endpoint, without passwords, private keys,
timestamps, or connection history. Probing alone never saves a key. Future VPS
actions verify the saved key automatically; a changed key requires explicit
verification before replacement. This trust record stays on this device and is
separate from device and VPS backups. Removing a server profile retains its SSH
trust record so it can still detect a changed key if that endpoint is used again.

Connection preferences are saved explicitly on this device, separately for each locally retained server. The private native store contains only current transport/network preferences, independent protection/reconnect/startup settings, routing mode and IP/application selections where supported, LAN bypass and MTU/optimization choices. It contains no connection timestamps, traffic samples, activity history, or credentials, and is separate from exported device and VPS backups. Saving a preference does not change or arm the active tunnel. Local removal clears that server's connection preferences.

SirinVPN has no operator-side data collection. There is no account system, analytics SDK, telemetry pipeline, crash uploader, SirinVPN-operated update endpoint, central server inventory, advertising identifier, or remote support endpoint.

The P2T/P2U/P2V/P2W release tool operates only on caller-selected local files, its compiled public trust root, and its fixed root-owned Linux release-state directory. A signed manifest contains the product name, release version and monotonic sequence, stable/preview channel, security-update boolean, artifact kind/target/filename/size/SHA-256, and declared persistent-state schema ranges. The receipt contains the pinned active public key, active signed manifest/signature and selected artifact declaration, plus the highest accepted signed manifest/signature. The cache retains the complete current package; during an unresolved Debian transaction it also retains the previous/candidate packages and a canonical journal containing only their public versions, manifest digests, targets, and artifact declarations. The separate trust record contains only the root-signed policy sequence/digest/signature, active public release keys, and permanently revoked public key IDs. None of these JSON formats contains a device, server, installation, account, request, network, analytics identifier, timestamp, source address, check result, or release history. Normal completion retains only the active package, receipt, and current trust snapshot; a newer policy overwrites the older snapshot rather than appending history. Key generation, signing, trust-policy authoring/verification, compatibility planning, receipt operations, offline Debian installation, and recovery perform no network request; `dpkg` receives a local root-owned package and a sanitized environment. Private keys are written once as mode-0600 local files and are neither copied into signed output nor printed.

P2X adds one explicit unprivileged HTTPS fetch command and no release service, default endpoint, background check, scheduler, or frontend network API. The caller supplies a base directory URL that cannot contain credentials, a query, or a fragment. A successful invocation sends at most five stable GET requests with a version-independent SirinVPN user agent: four fixed public metadata paths and the selected artifact filename. Proxy discovery, redirects, referers, and response encoding are disabled. The selected source and the operating system's DNS/network infrastructure necessarily observe the source IP, channel path, timing, and artifact filename, which can reveal the requested platform; SirinVPN attaches no device, server, installation, account, user, request, advertising, or analytics identifier. The source URL and check result are not stored. Only the current verified public metadata and artifact are atomically published in the caller-selected private local directory, with no request log or update history; ordinary failure removes staging. The separate root-owned coordinator re-verifies those files and retains only its existing current policy/receipt/cache model.

P2Y lets a Linux desktop user invoke that fetcher manually with a source typed for the current check. The source remains only in current form/native invocation memory and is never added to a profile, preference, history, log, or default. One successful candidate lives in an app-owned private temporary directory only until it is discarded, replaced, or the process exits normally; the frontend sees authenticated public release fields but no filesystem path. A hard-killed desktop/fetcher can leave a mode-`0700` `sirinvpn-desktop-release.*` tree in the operating-system temporary directory containing only the public signed candidate files; it contains no source/check record and may be removed after confirming no fetch is active. Debian installation can retain only the existing root-owned current trust policy, receipt, and authenticated package cache model. Applying a newer root policy may persist even if the separately authorized package transaction later fails. The desktop app itself has no launch update check, update timer, update account, device identifier, or SirinVPN-operated endpoint.

The Owner can separately configure signed VPS security updates. They are off by default and have no default source. Explicitly enabling them stores only the current HTTPS directory and stable-channel policy in a root-private file on that VPS and enables a daily timer there. The dedicated non-login download account cannot read the VPN's private identity or authorization files. Manual and scheduled checks use the same bounded, identifier-free fetch protocol; the chosen source can see the VPS IP, timing and artifact path. The VPS retains one latest outcome enum, current public signing policy, current and highest accepted signed releases, one compatible rollback executable, and at most one current checked candidate. No check history or diagnostic report is uploaded or retained.

VPS executable-update journals contain signed public release records, not authorization snapshots. SSH install/repair/removal guards temporarily retain private configuration, identity and authorization backups under a root-owned mode-0700 maintenance directory. They survive reboot only while recovery or final cleanup remains pending. Repair recovery preserves the latest authorization snapshot so revocations accepted during its health checks are not restored to an older state. Durable commit or completed recovery removes these temporary copies. Signing-policy revocations and release high watermarks are not rewound by repair. See [signed VPS updates](docs/signed-vps-updates-2026-09-06.md).

AppImage updates use the same explicit source and root-authorized public release metadata. The private client transaction keeps one installed receipt, one pending candidate while installation is unresolved, and one retained previous signed package for recovery. AppImage rollback never rewinds the accepted release/trust high watermarks. A portable installation uses a local hash of its AppImage path to separate its private state directory; that value is never sent to a release source. This flow records no checks, source URLs, installation times or activity history.

## Data kept on the client

On Android, credentials and sensitive operation checkpoints are encrypted with
Android Keystore in app-private storage excluded from automatic backup and device
transfer. The app stores current configuration and unfinished operations, not
traffic samples or connection history. Location permission is used to identify
Wi-Fi for the explicit trusted-network setting, not to request GPS coordinates
or record visited networks. See [Android storage and platform
boundaries](docs/android/security-and-platform.md).

On Windows, user identities and remembered credentials use user-scoped DPAPI and private ACLs. The LocalSystem service stores one machine-scoped DPAPI session under its protected ProgramData directory, containing only current intent and exact owned networking records. Current network fingerprints are salted; no SSID inventory or network-visit history is retained. Manual app updates retain authenticated public candidate/receipt/transaction data in a protected directory. The chosen HTTPS source can observe ordinary request metadata; no automatic desktop check or default source is added. Windows application routing retains up to 24 current executable paths and their native WFP path identities with the authenticated current account in that encrypted session. It retains no launch arguments, process IDs, launch times, connection destinations or selection history. Selections stay protected across recovery and server switches; explicit Disconnect clears them. The kernel driver exposes no user device interface and keeps no packet payloads or history. See [Windows implementation](docs/windows-integration-2026-09-07.md).

Diagnostics run only on request and keep one report in memory. Client checks use current native state; authenticated VPS checks inspect current service, interface, route, firewall, listener, DNS and resource conditions. The private DNS probe asks for the DNS root NS record through the tunnel; it does not inspect the user's queries. Unknown/free-form remote diagnostic text is discarded and recognized results use bounded, fixed local messages. Closing, changing profile or clearing results discards the UI report. Only an explicit Copy action exports the displayed sanitized text to the system clipboard. No report is automatically logged, uploaded or attached to a backup. See [current diagnostics](docs/current-diagnostics-2026-09-07.md).

The local profile store contains the server label and endpoint, tunnel addresses, public keys and certificates, a random local server ID, booleans/public capability data recording whether that VPS supports SirinVPN's IPv6 tunnel, and the authenticated UDP/TCP ports plus public server transport key when installed. It also contains the current endpoint generation and, only after a cross-host Owner restore until its handoff is created, the exact previous public endpoint. These are current recovery state rather than endpoint history; in-place restore records no predecessor and handoff creation clears it. The store contains no browsing or connection history. Profiles use the private platform configuration directory (mode 0600 on Linux, private ACLs on Windows).

The optional `network-policy.json` beside the profile store is a separate mode-0600 device-local selection preference. It contains a random 32-byte salt, the selected named profile, and at most one current successful server/network/transport tuple with a coarse seven-day expiry. Connection discovery asks NetworkManager only for the current connection UUID, never an SSID or BSSID; if that UUID is unavailable, it temporarily uses the physical default-route interface and gateway. Display-only name resolution is separate, as described above. The transient identity value is combined with the random salt and SHA-256 hashed before persistence, and the raw value is discarded. A success on another server or network overwrites the tuple, repeated success does not extend its current validity, and no failure, attempt, latency, traffic, or network history is added. A future-version or corrupt file is ignored for connection ordering and preserved rather than guessed or overwritten. Deleting this optional file resets the profile and cache without affecting server profiles, keys, the VPS, or an active connection.

Each server/device private identity is stored separately in the Linux Secret Service/keyring. If that facility is unavailable, SirinVPN uses a mode 0700 local directory containing mode 0600 files. An invitation creator temporarily holds a random bearer token and invitation-only bootstrap identity only long enough to display the long code and locally rendered QR; an invited device holds them only during decoding/enrollment. Neither representation contains a permanent authorized-device private key. The invitation result is cleared from desktop state when its dialog closes. The temporary runtime directory `/run/sirinvpn` is mode 0755 so the unprivileged desktop can read `client-state.json`, which is mode 0644; the operation lock remains mode 0600. The status file contains only a schema version, random local server ID, current protection/reconnect/fallback flags, current apply time, selected transport, current full/selected routing mode, local-network exception flag, the selected CIDRs when applicable, the private resolver address only when needed for exact local-exception cleanup, and, when configured, the deterministic private IPv6 tunnel address. It contains no private key or public VPS address, is overwritten rather than accumulated, and disappears on reboot. While either authenticated wrapper is active, `/run/sirinvpn/transport.json` is root-only mode 0600 and contains the current WireGuard private key plus the selected public relay configuration so the privileged local relay can authenticate; explicit teardown deletes it and reboot clears it.

Selected applications on Linux share a dedicated network namespace created only by an explicit launch. A root-only `/run/sirinvpn/application-network.json` records its current server/user ownership, tunnel source addresses, private DNS address and LAN preference. Private namespace DNS configuration is removed on teardown. The executable, arguments and narrowly permitted graphical environment pass through bounded stdin to a fixed privileged launcher; only the permanently unprivileged child receives them as execution input. SirinVPN retains no executable list, argument history, PID history or per-application activity. The launch form is transient. The child receives a private runtime view that hides host resolver and session-bus sockets while preserving supported display/audio access. Automatic reconnect retains that namespace; disconnect leaves existing processes open without their network link and clears the current network record. Ordinary applications and system DNS keep their usual configuration.

During an explicit current-device key rotation, fresh final and transitional identities are stored under new secret-store references. A mode-0600 recovery journal records the server/profile binding, replacement public identity, secret references, persistent/fallback protection choice, and current transition phase; it contains no private key. The journal exists only until the replacement tunnel authenticates and old/transitional secrets are removed. It is current recovery state, not rotation history.

On Linux, explicitly retained native connection intent can restore without an unlocked desktop keyring, so it stores the active WireGuard connection into `/var/lib/sirinvpn/desired-connection.json`. The directory is root-only mode 0700 and the file is mode 0600. It contains the active WireGuard private key, public IPv4/optional-private-IPv6 tunnel configuration, selected transport, public server transport key when needed, resolved VPS endpoint, independent guard/reconnect/startup choices, MTU settings and the current bounded routing/application policy. A custom policy also retains a compatibility full-tunnel request for reboot recovery by an older helper. For Automatic, it may contain up to four installed candidate transports with authenticated endpoint/HTTPS descriptors, public keys and MTU configuration; it contains no raw or hashed network identity, management private key, browsing data, DNS queries, traffic counters, failure, timing, attempt history, or network timeline. The current candidate is not written back to this file. Explicit disconnect removes it.

On desktop, “Remember login on this device” saves the current SSH login for a host in the operating system credential store after a pinned SSH authentication succeeds. The record contains the host, SSH port, username, authentication method, optional password, private-key file path and passphrase, optional sudo password, and verified host-key fingerprint. No plaintext file fallback is used. The interface receives only the username, port, method, and optional key path; saved passwords and passphrases stay in native code. A saved login cannot be reused for a different host, port, or SSH key. “Change login” allows replacement and “Forget login” deletes the wallet record. Removing a SirinVPN profile or installation retains this host login for future setup; use Forget login to delete it. SSH logins are excluded from both device and VPS backups.

With remembering disabled, SSH credentials are held only for the current operation. Form secrets are cleared when the operation ends or its dialog closes, and native buffers are zeroized where practical. Desktop private-key files are read by the local SSH library and are never copied into the credential store. The SSH private key is never uploaded.

An encrypted device backup is created only after an explicit user action at a user-selected path. Its clear envelope contains the backup format/version, fixed KDF settings, random salt, random nonce, and ciphertext. The server label/address/ID, certificates, connection configuration, WireGuard private key, and management private key are inside the authenticated ciphertext. The network profile, salt, and current-network success preference are deliberately excluded. The password is not stored in the file or local configuration and is cleared from native/UI state after the operation where practical. Export and import perform no network request, and SirinVPN never discovers, indexes, synchronizes, or uploads backup files.

An encrypted server-state backup is likewise created only after a disconnected current Owner explicitly selects a new local path, confirms the sensitive export, verifies the VPS SSH host key, and supplies a password. Over that direct SSH session, a staged copy of the locally packaged server validates and returns a bounded snapshot containing the VPS's current SirinVPN configuration, WireGuard and management private identities, optional authenticated-transport private identity, and authorization, including its current port-forward set. Expired invitations, enrollment receipts, and pending rotations are omitted from the snapshot without rewriting VPS state. Generated operating-system configuration, host-specific interface/SSH-port metadata, SSH credentials, local device private identities, metrics, logs, DNS queries, and activity history are excluded. Snapshot plaintext exists only in bounded zeroizing process memory, is never written remotely, and is encrypted locally into a distinct authenticated mode-0600 no-clobber file. SirinVPN does not discover, upload, synchronize, or index that file.

During explicit server restore, the selected encrypted file is bounded, authenticated, decrypted, and matched to the existing local Owner profile before the destination SSH session begins. Plaintext state exists only in bounded zeroizing client/server process memory and is streamed through SSH stdin after the destination rollback guard is armed; it is not written as a local or remote archive, placed in command arguments, or logged. The destination stores only the restored current SirinVPN configuration, identities, and authorization plus deterministically reconstructed operational files. A successful migration updates the endpoint/capability fields of only the initiating local Owner profile and records its predecessor for the later explicit handoff. The old VPS and other devices' local profiles are not contacted or changed during restore.

When the Owner explicitly creates an endpoint handoff, the restored VPS signs public claims containing the server name/ID, exact old and new public endpoints, generation, public server identities, fixed tunnel layout, public IPv6/transport capabilities, and a SHA-256 fingerprint of the current member/device authorization snapshot. The fingerprint detects clone divergence without adding a second copy of the member/device records to the code. The resulting `sirm1.` code contains no device credential or private key. It exists in desktop memory while the dialog is open and wherever the user deliberately copies it. Publishing sends the same claims to the old VPS only through its private authenticated management connection and stores one boolean handoff-source marker there so later authorization mutations fail rather than fork; applying retrieves or decodes the claims, temporarily connects to the new VPS, and replaces only the current profile after authenticated proof. SirinVPN does not upload, synchronize, index, or retain a client-side history of endpoint codes.

## Data kept on the VPS

The VPS stores its WireGuard private key, management private key, separate authenticated-transport private key when installed, current configuration (including public IPv6/UDP/TCP capabilities, Recursive or explicitly configured DNS-over-TLS/HTTPS endpoint IP and TLS names, the DoH paths when selected, and up to 64 explicitly configured private DNS names/IP addresses and bounded split-zone suffix/upstream configuration), owner certificate, and current Owner/Admin/Member assignments in `/etc/sirinvpn`. A separate host-specific mode-0640 operational file retains only the current external-interface name and SSH server port so reserved-port validation and exact firewall rules can be reconstructed; it is not a connection or interface history. Private records and secure-resolver endpoints are current shared VPN configuration; every authorized device can read that current set through the mutually authenticated private management API. They are not copied into client profiles, invitations, device backups, helper state, or connection history. The separate authorization document stores only current members and their current suspended/active state, current devices and their public identities, each device's current peer-communication boolean, up to 32 current exact protocol/public-port/device/device-port mappings, current member limits/expiration/UTC schedules/delegated permissions, active invitations with bounded remaining uses, short enrollment retry receipts, any explicitly prepared device-key rotations for at most ten minutes, and at most one latest signed endpoint transition. Peer permission defaults false and the mapping set defaults empty; both record only current authorization, not when, why, or by whom it changed. SirinVPN does not retain peer-flow or forwarded-flow metadata. Incoming forwarded packets are source-NATed, so the target normally sees only the gateway `10.77.0.1`; the target application and unrelated VPS facilities remain outside SirinVPN's storage boundary and may independently log what they receive. IPv6 tunnel addresses are derived when needed from the existing random server ID and IPv4 device addresses rather than stored as activity records. A pending rotation contains only its random identifier, current device/fingerprint binding, replacement public keys/certificate, and expiry. A transition contains only the public signed handoff fields described above and replaces the previous transition rather than accumulating a chain. Expired invitations, receipts, and rotations are removed rather than archived. Suspending a member retains their public device identities, assigned addresses and settings for reactivation, while cancelling their pending invitations, receipts and rotations. Bulk revocation removes their devices, forwards and pending access. Neither operation records an actor, reason, timestamp or event history. It does not persist role-change, peer-policy-change, port-forward-change, rotation, or endpoint history, connection events, client source history, destinations, bandwidth history, DNS queries, resolver success/failure history, authentication-attempt history, or packet metadata.

The current server status also exposes root-filesystem used/total bytes and aggregate VPN-interface packet totals. The authorized membership view reduces current WireGuard handshake times to an optional recent-activity boolean (within three minutes), using only public peer keys to match existing devices. Raw timestamps and runtime endpoints are not returned, logged, written to authorization state, or included in backups. Idle includes devices that may be offline; missing data remains unknown. The device screen replaces its current snapshot every ten seconds while visible.

Clients display current aggregate counters, concrete transport, routing, DNS and quality/MTU observations. They overwrite or expire the current snapshot instead of storing a timeline. Selected routes and application choices are local configuration, not uploaded activity. Automatic recovery observes current physical routes and authenticated handshake freshness; Linux voluntary transport comparisons use isolated leased peers under protection; older Windows comparisons retain their protection/idle conditions. One current comparison and route epoch remain volatile, while the separately documented desktop cache can retain one salted successful selection for its bounded validity. Signed endpoint discovery reads only current authenticated endpoint state and is governed by reconnect policy. No public address/speed-test service, packet capture or attempt history is used.

The authenticated transport server keeps only current relay state in memory. A UDP session holds the authorized public device key, current source socket address, replay state, and last-seen time needed to return packets and accept NAT roaming; idle sessions are discarded after three minutes. A TCP connection holds the authorized public device key, Noise state, ordered nonces, and one connected loopback UDP backend until it closes, is revoked, or remains idle for three minutes; global and per-device counts are bounded. A separate in-memory status marker retains only the public device key, concrete transport, and monotonic last-seen instant. Candidate-probe counters and handshake replay digests are bounded and memory-only. None of this state is logged, persisted, exposed as history, or retained across daemon restart.

The VPS daemon reads aggregate CPU counters and memory totals from `/proc`, plus aggregate byte totals for the SirinVPN interface. It retains exactly one previous sample and its monotonic timestamp in process memory so it can calculate current rates; every new sample replaces the prior one, and a daemon restart discards it. Samples contain no member/device association, destination, DNS query, or packet metadata and are not written to disk or service output. The management API creates a random request identifier in each live response, but neither endpoint persists it.

## Network communication

The client communicates directly with:

- the VPS over SSH during provisioning, explicit Owner repair/update, or explicit Owner uninstall;
- the VPS over SSH during an explicit Owner server-state export or restore;
- the selected VPS Direct WireGuard, Obfuscated UDP, pinned TLS/HTTPS or TCP fallback endpoint while connected;
- the private management endpoint inside the tunnel;
- the old and restored VPS private management endpoints during an explicit signed endpoint handoff;
- the same VPS directly during invitation enrollment;
- the explicitly configured DNS-over-TLS or DNS-over-HTTPS resolver IP addresses from the VPS when that policy is enabled;
- the explicitly selected HTTPS release directory during a manual client update check, or an enabled VPS security-update check;
- the private VPS address for current quality, MTU and diagnostic probes, and authenticated endpoint discovery where configured;
- destinations and DNS infrastructure selected through ordinary internet use.

The desktop frontend contains no web request API and the native management client disables proxy discovery. Repair uploads only the server artifact already packaged on the local device to the selected VPS; it performs no update check or release download. SirinVPN does not contact a developer-controlled host.

The opt-in Linux outbound-network audit runs the CLI in a dedicated cgroup and uses policy-accept nftables counters to prove the current manual transport paths contact only the selected VPS, its private management endpoint, and its private resolver. Dedicated VPS service cgroups separately constrain observed daemon traffic to authenticated listener replies, the WireGuard relay bridge, private management/DNS replies, and the Owner-configured encrypted resolver endpoints. Anything outside that documented TCP/UDP ownership map fails the gate. The observers retain only aggregate in-memory counts, capture no payload or discovered destination, and are removed with exact local/VPS baseline verification. This dynamic lane currently covers an IPv4 Linux Owner using DNS-over-TLS; the static privacy gate remains responsible for repository-wide bans on telemetry/reporting dependencies, production logging, direct frontend web transports, unexpected URL literals, and activity-history fields.

Device-key rotation uses only the existing tunnel and private VPS management endpoint. Only the fresh public WireGuard key and self-signed management certificate leave the device; neither replacement private key is transmitted.

The hosting provider can know the VPS account and network traffic. Internet destinations reached through the tunnel can observe the VPS IPv4 or NAT66 IPv6 egress address. Two VPN devices whose current peer settings are both enabled can address each other's tunnel IPs and observe the traffic they deliberately exchange; the VPS forwards those packets without creating peer-flow or policy-change history. In selected-route modes, unlisted destinations instead remain visible to the local network/ISP and observe the device's normal egress address; Application selection is explicit where the platform supports it; SirinVPN does not infer destination routes from DNS activity. System DNS still goes to the VPS, while an application's own encrypted DNS connection follows the route to that resolver's IP. Recursive resolution exposes normal iterative queries from the VPS to authoritative DNS infrastructure; DNS-over-TLS and DNS-over-HTTPS expose queries to the resolver provider the Owner selected while encrypting/authenticating that VPS-to-resolver hop. DoH reuses bounded HTTPS connections and sends no cookie or application identity, but the resolver can still correlate queries from the VPS address and normal HTTP/TLS connection metadata. A query answered by an exact configured private record stays within the client-to-VPS tunnel and does not require the upstream. These are normal third-party boundaries, not data received by SirinVPN developers.

Removing a server profile is refused while it owns an active or reconnecting tunnel. After disconnect, local removal deletes the profile, its local secret, and the one cached success if it belongs to that server, but deliberately leaves the selected named network profile and VPS installation intact. A current Owner may instead explicitly choose clean server-side uninstall through a fresh host-key-pinned SSH session; the operation verifies current VPS ownership, removes only SirinVPN-owned state under a rollback guard, and deletes the local profile only after remote verification succeeds. Admin and Member devices can remove only their local state.

A current Owner may also explicitly repair/update the VPS while disconnected. The operation reads current SirinVPN identity/configuration, DNS upstream, private-record set, and network capability over the pinned SSH connection, uploads the locally packaged server executable plus the public Owner certificate, and rewrites SirinVPN-owned operational configuration transactionally. It may update the local profile's public IPv6, Obfuscated UDP, and TCP fallback capability data and may preserve or explicitly replace/clear the VPS DNS policy and private records; it does not send the local management or WireGuard private key, contact a release service, record DNS queries, or create repair history.

A current Owner may explicitly export VPS recovery state while disconnected. This read-only operation stages the locally packaged server executable and public Owner certificate, streams the validated snapshot into client memory, deletes those staged public/candidate files, and encrypts locally. It does not reconfigure or restart the VPS, send the backup password or destination over SSH, or create a remote snapshot file.

A current Owner may explicitly restore that state to a pinned Debian 13 VPS while disconnected. The destination receives the packaged candidate and bounded snapshot bytes over SSH stdin, then writes only SirinVPN-owned state inside the existing rollback transaction. If replacement was explicitly selected, the destination's earlier SirinVPN-owned state is first captured in a root-owned reboot-persistent maintenance directory for rollback; unrelated VPS paths and services remain outside the transaction. The backup password and local source path never reach the VPS. Commit changes the initiating device's local public endpoint only after exact remote verification. Restore itself does not contact or uninstall the old VPS. A later Owner-requested endpoint handoff may publish the public signed transition to that old VPS and let other authorized devices verify the restored endpoint; it retains no history and still does not uninstall either host.
