# Security model

SirinVPN is designed to protect traffic between authorized Linux, Windows, and Android clients and one user-controlled VPS. It does not make the VPS provider, destination services, upstream DNS infrastructure, or the network path cease to exist.

Android uses a separate native VPN process and same-UID Binder calls, with
Keystore-protected credential storage. See the current [Android security and
platform boundaries](docs/android/security-and-platform.md). Historical Android
audits apply only to their named builds, not to the current port.

## Implemented security properties

- Every server profile receives a unique local WireGuard key and a unique Ed25519 management identity.
- Private key material is generated locally. It is not uploaded to a SirinVPN service because no such service exists.
- P2T release manifests are deterministic, bounded, strict JSON signed with a domain-separated Ed25519 signature over the exact manifest digest. Verification requires an independently trusted public-key fingerprint and then authenticates each regular non-symlink artifact's exact filename, target slot, byte length, and SHA-256. Manifests also bind SemVer, a monotonic per-channel sequence, and security-update classification. The transition planner rejects product/channel changes, inconsistent version/sequence movement, implicit downgrade, changed state families, a candidate unable to read current schemas, or a candidate write that the current release could not read after rollback. The signing tool writes a new private key mode `0600`, never replaces key or manifest outputs, and makes no network request.
- P2U adds one root-owned Linux receipt and authenticated active-package cache under `/var/lib/sirinvpn-release`. Its canonical active binding contains the complete verified manifest/signature and selected exact artifact declaration; a second complete signed record retains the highest accepted release. The externally trusted public key is canonicalized and pinned on first commit. Subsequent state plans/commits reject key substitution, active/high sequence reuse with different manifest bytes, implicit rollback, below-watermark upgrades, incompatible state formats, receipt or cache tampering, unsafe file types/links, and incorrect ownership/modes. Explicit rollback never lowers the watermark, exact commit retry does not rewrite it, and atomic replacement is serialized, file-synced, and directory-synced. This protects the normal update path from unprivileged replay; root can replace both program and state.
- P2V wraps an already bound same-target `sirin-vpn` Debian package in an offline transaction. The receipt lock and Linux network-operation lock exclude competing state writers and tunnel operations. Both current and candidate cached bytes, signed state compatibility, Debian package identity/version/architecture, and fully disconnected nonpersistent state are checked before mutation. A canonical root-only journal precedes fixed-path, no-shell `dpkg`; configured version, package-file verification output, fixed executable ownership/modes, the new release binary version, and helper state must pass before the receipt advances last. Failure automatically reinstalls and verifies the previous authenticated package; an unproven rollback retains both packages and the journal for idempotent recovery. The receipt decides recovery after an interrupted final commit. Deterministic VM crash points compile only under the non-default `test-release-fault-injection` feature and require a separate confirmation value; production packages are built without it. P2V does not trust apt caches, contact repositories, fetch dependencies, update AppImages, run at boot, or couple a client package update to VPS Repair. Root and trusted maliciously signed package contents remain outside this boundary.
- P2W embeds one public Ed25519 release root and domain-separates its signatures from release manifests. The offline root signs canonical bounded key-policy snapshots with a strictly monotonic sequence, a nonempty bounded active-key set, and a permanently accumulated revoked-key set. The root cannot authorize itself for ordinary releases. Installed policy replacement is serialized with receipt/package mutation, atomic, file/directory synced, and idempotent. Older policy sequences, changed bytes at the same sequence, un-revocation, silent active-key removal, wrong roots, noncanonical data, and unsafe paths fail closed without replacing a valid policy. Once policy state exists, caller-supplied keys cannot bypass it. A new authorized key can replace the receipt pin only on a strict release upgrade above the durable high watermark; cross-key rollback/rebind is refused. Recovery continues to authenticate a pre-commit previous receipt independently, so revocation cannot strand an interrupted package transaction. The immutable root private key and malicious root-signed policy or release contents remain outside this boundary. The current public root is pre-distribution bootstrap material and is not production authority until its private half has encrypted offline custody and a tested backup.
- P2X keeps network retrieval outside the signer/verifier and privileged coordinator in a separate unprivileged process. It accepts only a caller-selected credential/query/fragment-free HTTPS directory, disables proxy discovery, redirects, referers, and response decompression, and uses native CA validation with fixed connect/read/total timeouts. One invocation requests four fixed public metadata names and, only after the bundled root authorizes both policy and manifest signer, one selected signed artifact. Every response and target is bounded; a declared or streamed size mismatch, non-200 response, encoded body, wrong channel, invalid signature, or digest change fails before publication. A verified bundle is file-synced and atomically renamed without replacement into a new normalized absolute mode-`0700` directory with mode-`0600` contents. Ordinary failures remove staging. A killed process may leave only a private hidden staging directory, never the requested final path. A malicious or compromised HTTPS source can observe the connecting IP and requested artifact, withhold data, or replay an authentic older snapshot, but cannot forge accepted bytes; installed policy and receipt high-watermark checks remain independently authoritative. Compromise of the platform CA store can expose or deny retrieval but cannot replace the Ed25519 provenance chain. P2X does not install, run on a schedule, resume downloads, or add a default central endpoint.
- P2Y exposes that retrieval path only through an explicit desktop action. Production builds resolve the packaged unprivileged fetcher without an environment override, strictly bind its bounded JSON result and every private regular file to the desktop-created candidate paths, and retain at most one candidate in a session-scoped temporary directory. The web layer receives only authenticated public release metadata, never a local candidate path. Closing or replacing the check drops the candidate. Installation requires a second exact-package confirmation, a newer release, the root-owned installed Debian build, and fully disconnected nonpersistent helper state; the privileged coordinator repeats the network-lock and complete provenance/package checks through fixed `pkexec` and coordinator paths without a shell. Rollback is not exposed. Applying trust and installing the package are independently authorized root operations: if the package stage fails, a valid newer root policy may remain; authenticated rollback is attempted, and an unproven result retains both packages and the journal for recovery without advancing the receipt. Exact retry remains safe. AppImage self-replacement, default sources, automatic checks, background scheduling, notifications, dependency fetching, and VPS Repair remain outside this boundary.
- The Linux Secret Service/keyring is preferred. If it is unavailable, the fallback directory is forced to mode 0700 and each atomic secret file to 0600.
- Windows delegates adapter, route, DNS, transport and WFP changes to a LocalSystem service through bounded named-pipe commands. Both sides authenticate the peer; the service binds a session to the impersonated caller SID and rejects cross-user replacement. WireGuardNT loads only from an absolute protected path with a pinned hash. User identities use user-scoped DPAPI; current service intent uses machine-scoped DPAPI with SYSTEM/administrator ACLs. Owned routes and filter conditions are checked exactly. Persistent WFP blocks survive service loss; active adapter/carrier permissions are dynamic. Explicit Disconnect journals cleanup before removing intent. Service restart, new boot, reconnect and startup are distinct policies. See [Windows boundaries and evidence](docs/windows-integration-2026-09-07.md).
- Current diagnostics require valid local profile/identity bindings and, for remote checks, the matching active tunnel plus pinned mTLS. Server authorization is checked before and after collection. Bounded probes address only the private server/DNS; command output, time and concurrency are capped. Sanitization accepts known codes and fixed local messages, discards arbitrary remote text, and reports inaccessible evidence as unavailable. Listener/firewall structure and configured routing are not advertised as packet-level leak proof. Reports are volatile and export only through explicit Copy. See [diagnostics evidence](docs/current-diagnostics-2026-09-07.md).
- Secret-bearing Rust values and serialized buffers use zeroization where practical. SSH passwords and passphrases are never accepted as command-line arguments or environment variables.
- A device backup contains one profile plus its complete WireGuard and Ed25519 private identity. Export requires an explicit sensitive-data confirmation and a password of at least 12 characters, derives a 256-bit key with fixed Argon2id v19 parameters (64 MiB, three iterations, one lane), and authenticates/encrypts the payload with a random-salt, random-nonce XChaCha20-Poly1305 envelope. Files are capped at 256 KiB, created atomically as mode 0600, and never overwrite an existing path.
- Device restore accepts no file-selected KDF cost, rejects unknown format/algorithm versions before allocation, combines wrong-password and tamper failures, validates private/public identity bindings, and refuses duplicate identities or conflicting server IDs. A fresh local secret reference is staged before an insert-only profile commit and removed if that commit fails. Device restore is offline; it neither changes VPS authorization nor revives a revoked certificate.
- Server-state export is available only to a disconnected current Owner through a fresh host-key-pinned privileged SSH session. A bounded staged candidate binary validates the current server configuration, private/public WireGuard and management-key bindings, authorization schema/server ID, and exact current Owner-device certificate before emitting state; it does not replace the installed binary. The snapshot contains only the current configuration, WireGuard and management private identities, optional transport private identity, and current authorization, with expired transitional authorization records pruned in the snapshot only. It is bounded to 2 MiB, retained in zeroizing memory, streamed directly over SSH, and never written as plaintext on the VPS or client. The client uses the fixed Argon2id/XChaCha20-Poly1305 envelope under a server-backup-specific authenticated format, caps the encrypted file at 4 MiB, and creates it atomically as mode 0600 without overwrite. The password and destination never enter remote commands. The encrypted file plus password can clone the VPS identity and authorization and must be protected accordingly.
- Server restore is available only to a disconnected device that still holds the matching current Owner identity. Before SSH, the client bounds and authenticates the encrypted file, rejects unsupported versions/KDF declarations, validates every stored private/public binding, and matches the server ID, tunnel layout, public server identities, and Owner profile. The destination requires a fresh host-key pin and explicit replacement consent when any exact SirinVPN-owned state exists. Only after snapshotting that target state and arming the five-minute rollback guard does the client stream plaintext through SSH stdin to the staged current server candidate; no password, snapshot, or plaintext archive enters a remote command or file. The candidate validates authorization and cryptographic bindings before writing the intended private fields, then the installer reconstructs generated state and verifies identities, modes, services, network/firewall/NAT, DNS, listeners, artifact digest, and SSH reachability before commit. Failure restores the destination's prior SirinVPN-owned state, and local profile mutation occurs only after remote commit. A stale backup can reauthorize devices that were revoked after export. Successful migration updates only this Owner device's public endpoint and records the exact predecessor locally; it does not modify the old VPS during restore.
- Endpoint distribution is an explicit post-restore operation. The restored VPS signs the exact predecessor, candidate, monotonic generation, server/WireGuard/TLS identity, tunnel layout, public capabilities, and a canonical SHA-256 fingerprint of the current members/devices with its existing pinned Ed25519 management key. Only an authenticated current Owner can create or publish the transition, and invitation/enrollment/key-rotation transitions must be quiescent. Old-VPS publication refuses if its member/device fingerprint has diverged from that signed snapshot. The signed code is public recovery data, not an access credential. A receiving device must match the predecessor and generation exactly, then reach the candidate through WireGuard and prove pinned mTLS, its current device identity, and the identical server-published transition before atomically updating its profile. Tamper, replay, skipped-generation, wrong-profile, activation, or authentication failure leaves the prior profile unchanged and requires complete candidate cleanup. Publishing on the old identity clone is explicit, persists a read-only handoff-source marker, and does not uninstall it; the old server continues authenticated reads but refuses enrollment and authorization/key mutations to prevent split-brain state. Only the latest transition is retained, so every device must move before the next migration.
- The privileged helper accepts tunnel configuration only over stdin. Release builds ignore environment variables that could redirect privileged helper or server executables.
- Linux routing is either compatibility-defaulted full tunnel or an explicit list of 1–32 canonical, unique, non-default IPv4/IPv6 CIDRs. The unprivileged desktop/CLI normalizes the list and the root helper independently rejects malformed, non-canonical, oversized, legacy-schema, default-route, or unsupported-IPv6 input before changing networking. WireGuard and table `51820` receive only those destinations plus the exact private DNS `/32`; no DNS observation, application name, or packet history can create a route. The optional local-network override is a fixed private/link-local/multicast set at reserved priorities, with a higher-priority private-DNS route.
- The unprivileged transport engine resolves validated profile capabilities to concrete Direct UDP, Obfuscated UDP, pinned TLS/HTTPS or raw TCP selections. Manual choices stay pinned. Automatic uses a bounded advertised plan and authenticated readiness through the tunnel; teardown must be proven before fallback. All four transports support retained current intent. Local preferences cannot add a capability or bypass the privileged platform validation. Unknown request/state versions fail closed; complete current compatibility declarations live in `release/state-compatibility.json`.
- The optional desktop network-policy store is private and atomically replaced under its lock. It contains a random salt, named preference, one bounded current success and explicitly configured trusted-network labels/fingerprints. Desktop recognition uses current platform identifiers without requesting SSIDs/BSSIDs; raw identifiers, failures and attempt history are not stored. Corrupt/future documents are preserved. Editing an unprivileged preference cannot add capabilities, bypass native validation, satisfy Noise/mTLS or change VPS authorization.
- Obfuscated UDP uses Noise IK (`25519`, ChaCha20-Poly1305, SHA-256) with a per-installation server static identity and the current device's authorized WireGuard X25519 identity. Its explicit per-direction nonces, 128-packet replay windows, bounded handshake replay cache, encrypted length framing, and random padding protect the wrapper; WireGuard still independently authenticates and encrypts the inner VPN packet.
- The public Obfuscated UDP listener emits no response for malformed, replayed, or unauthorized handshakes and bounds candidate handshakes per source IP in memory. This raises the cost of active identification but is not a claim of DPI-proof or indistinguishable traffic.
- TCP fallback uses the same Noise IK identities under a distinct protocol prologue, ordered per-direction nonces, bounded encrypted datagram records, and variable padding. Its listener caps global connections and each authenticated device, rate-limits candidate connections per source, rejects replayed handshakes, and emits no application bytes to malformed or unauthorized probes. It is intentionally not TLS/HTTPS camouflage and remains fingerprintable or blockable.
- TLS fallback carries authenticated bounded datagrams inside real TLS 1.3 with a distinct Noise binding and an exact authenticated certificate pin. Legacy framing remains readable. Optional HTTPS uses a configured hostname/path, bounded WebSocket upgrade and masked client frames; the server authenticates Noise before 101 and gives generic static web/404 responses to ordinary or unauthorized requests. Generated or explicitly imported matching certificates are pinned; renewal does not silently replace a client pin. This does not establish browser-identical fingerprints or resistance to every active probe. See [HTTPS transport](docs/https-transport-2026-09-06.md).
- SSH host keys require an explicit SHA-256 pin. A mismatch stops installation before privileged changes.
- The installer never flushes or changes the policy of the host firewall. It owns `sirinvpn_filter`, `sirinvpn_nat`, and, only on an IPv6-capable VPS, `sirinvpn_nat6`; their chains use an accept policy so the existing SSH path is not replaced. If Docker exposes its supported `DOCKER-USER` boundary, SirinVPN adds only an exact, comment-tagged pair for each enabled address family; stop and rollback remove only those exact rules.
- Before changing SirinVPN-owned networking, the installer snapshots its earlier files, service activation state, IPv4/IPv6 forwarding state, and any IPv6-uplink router-advertisement setting it changes in a root-owned reboot-persistent maintenance directory. Failure restores the snapshot immediately; interruption triggers a systemd rollback timer.
- A claimed server accepts an idempotent reinstall only from a device belonging to the current Owner in the VPS authorization document. A legacy installation without that document falls back to its original bootstrap Owner certificate. A lost Owner can use the explicitly configured [recovery mechanism](docs/offline-owner-recovery-2026-09-06.md) with pinned privileged SSH and the required recovery material. Full replacement remains a separate destructive choice. The replacement backup and rollback guard are armed before old SirinVPN keys or authorization are removed; successful replacement intentionally revokes every former SirinVPN device and invitation but does not delete unrelated VPS state.
- Remote uninstall is exposed only to a current local Owner profile and requires a fresh host-key-pinned root/sudo SSH session. Before mutation, the current VPS authorization must bind that device certificate to the sole Owner and the authorization server ID must match the local profile. A five-minute rollback guard is armed before SirinVPN services or files are removed, verification precedes commit, and local profile/key deletion happens only after the remote transaction succeeds. Admins and Members can perform local removal only. Uninstall removes an exact SirinVPN-owned path/rule set and retains generic Debian packages and unrelated services.
- Repair/update is exposed only to a disconnected current local Owner through a fresh host-key-pinned root/sudo SSH session. Before mutation, read-only preflight requires the authorization server ID, sole current Owner certificate and WireGuard key, server WireGuard public key, pinned management TLS certificate, fixed tunnel layout, and supported schema to match the local profile. A legacy P0 state has no authorization server ID, so it is instead bound by its original Owner certificate plus both server cryptographic identities before compatible authorization expansion. Initialization then creates a root-owned authorization-required marker; if authorization later disappears, both server startup and repair fail closed rather than recreating an Owner database. The locally packaged candidate proves the stored WireGuard, management TLS, transport, and derived TLS-fallback certificate bindings plus authorization compatibility. Missing/corrupt cryptographic state fails closed rather than rotating identity. The existing install rollback transaction reconstructs only SirinVPN-owned state, refuses to replace an unrelated TCP/443 listener, and verifies the installed digest, exact ownership/modes, services, interface/address/key/ports, firewall/NAT, forwarding, private DNS and management listeners, and original SSH session before commit. Repair may add public IPv6/Obfuscated-UDP/raw-TCP/TLS capability fields and, on the first transport migration only, a separate server transport identity; it preserves all existing WireGuard, management TLS, device, authorization, and previously created transport identities. Shared-port migration and later explicit port changes validate listener conflicts and preserve the authenticated endpoint binding; see [endpoint configuration](docs/endpoints-and-outer-ipv6-2026-09-06.md).
- DNS upstream policy accepts only Recursive or one/two typed DNS-over-TLS/HTTPS endpoints composed of a usable unicast IP address and a bounded TLS authentication name; DoH additionally requires a canonical absolute path. No free-form Unbound, record, shell, port, URI authority, query string, or certificate-path fragment crosses the installer boundary. DoT fixes TCP/853 and the system CA bundle. DoH fixes HTTPS/443 and RFC 8484 POST wire messages, uses native CA roots and the configured name for TLS while pinning resolution to the exact endpoint IP, disables system proxies and redirects, bounds message size/concurrency/timeouts, and validates response status, media type, DNS transaction, and opcode. Its separate unprivileged service has no capabilities, logs nothing, listens only on loopback UDP/TCP, and has systemd network access only to loopback and configured resolver IPs. Unbound covers the root zone and sets `forward-first: no` for either forwarding mode, so failure cannot trigger recursive or plaintext fallback. Private DNS accepts at most 64 exact canonical A/AAAA records and serves them only on Unbound's loopback/tunnel listeners. The guarded installer verifies exact generated directives/counts, Unbound syntax/listeners, the policy-specific DoH service/listeners, and rollback state before commit. Empty Recursive/DoT/DoH are accepted only as schemas 1/2/4; private records use schema 3 with Recursive/DoT and schema 5 with DoH. Explicit switching/clear contracts to the destination policy's schema before binary rollback. Split DNS adds typed, bounded private suffixes and exact-IP upstreams, generated and verified inside the same transaction; no raw resolver syntax crosses the boundary. Explicit diagnostics perform bounded current root/zone queries and distinguish upstream outcomes without retaining query or reachability history. See [split DNS](docs/split-dns-2026-09-06.md).
- The management service listens only on the private tunnel address (default `10.77.0.1:8443`), uses TLS 1.3 only, requires a current device or active bootstrap certificate, and has no unauthenticated application endpoint.
- Invitations are signed by the pinned VPS identity, bound to one server and their permitted access scope, strongly random, expiring, explicitly cancellable and rate-limited without attempt history. Single-use invitations and explicitly bounded reusable invitations enforce their current use limits and exact retry receipts. Member invitation policy, device limits, expiration, UTC schedules and delegated permissions are revalidated against current authorization. Secret codes never enter CLI process arguments. QR images are rendered locally from a bounded compressed representation of the same bearer invitation.
- Every permanent invited-device identity is generated on that recipient device. Only public keys and certificates are submitted during enrollment; permanent private keys are neither copied from the owner nor placed in an invitation code.
- Current-device key rotation generates a fresh WireGuard key and Ed25519 management identity locally for any authorized Owner, Admin, or Member device. Preparation persists only a new public identity, the current device binding, and a ten-minute expiry in authorization state. The pending certificate is admitted at TLS but is authorized only to commit or cancel its matching rotation; it cannot read status or use another management mutation. Commit must arrive through that new private certificate while the old WireGuard peer is still active, then replaces both public keys with the existing peer-first/write/peer-rollback transaction. The old certificate and peer stop authenticating after commit, while device ID, address, role, and unrelated authorization remain unchanged.
- The client stages transitional and final private identities under fresh secret-store references and writes a mode-0600 journal containing no private key. A lost commit response is resolved by authenticating the final identity first, then the old identity; retry is idempotent and an uncommitted server transition expires without changing the device. The original and transitional local secrets are deleted only after the new tunnel and management fingerprint are verified. The optional Automatic-fallback flag is journaled with persistent protection so rotation cannot silently pin the restored session. Corrupt journals fail closed, and a recoverable journal remains visible until cleanup completes.
- Current Owner/Admin/Member authorization is checked for every management mutation. Admins cannot modify Owner/Admin targets or create Admins, only the Owner can change Admin access, access changes cannot race active/recent device enrollment, and the final Owner device cannot be revoked. Ownership transfer is re-authorized while holding the authorization write lock, identifies an existing destination device, blocks affected in-flight enrollment handoffs, and atomically swaps the sole Owner while retaining the previous Owner as an Admin.
- Device revocation removes the WireGuard peer before committing current authorization and every API handler rechecks the caller certificate. If persistence fails, peer state is restored to the last committed document.
- Direct VPN-peer forwarding is default-deny. A packet is admitted only when both exact current source and destination tunnel addresses are in authorization-derived nftables sets; a new, revoked, disabled, failed-start, or stopped-server device remains isolated while its private DNS, management, and internet paths keep their existing boundaries. The Owner may manage every device, an Admin only ordinary Member devices, and a Member only their own explicitly delegated scope. This device-scoped all-enabled mesh is separate from client LAN access and does not provide pairwise/group ACLs, discovery, or VPS-LAN access.
- Public-to-device forwarding is also default-deny and IPv4-only. Each current rule names one protocol, one high public port, one current device, and one device port; there are at most 32. The Owner can target every device, an Admin only ordinary Member devices, and a Member only their own explicitly delegated scope. Low ports plus the active SSH, private-management, DNS-proxy, WireGuard, and authenticated-transport ports are reserved. The DNAT rule sets a private connection mark; an exact pre-Docker filter rule must match that mark, original public port, target address, protocol, and target port before setting the packet mark used by the scoped `DOCKER-USER` continuation. Unmarked unsolicited external traffic to the tunnel subnet is dropped. Removing a rule or revoking its device atomically removes current admission; marked established flows hit an earlier stale-flow drop instead of the ordinary established-reply allowance. Daemon stop flushes the filter chain before its NAT chain, so a crash, failed start, or binary downgrade cannot leave public admission behind.
- Forwarded connections are source-NATed to `10.77.0.1`, making replies deterministic for full- and split-tunnel clients but hiding the visitor's original source address from the target service. The feature does not inspect whether a device service is safe, does not configure a provider firewall, and supplies no source allowlist, port range, automatic mapping protocol, hostname router, or IPv6 ingress. The confirmation is a security boundary, not a claim that the exposed service is hardened.
- The server daemon runs with only `CAP_NET_ADMIN` for validated WireGuard peers, exact peer-isolation sets, and exact current port-forward chains, plus `CAP_NET_BIND_SERVICE` for the default public UDP+TCP/443 listeners, under restrictive systemd sandboxing. It can atomically write only `/etc/sirinvpn/authorization`; it can read the mode-0640 host-specific operational metadata and mode-0600 transport key but cannot read the root-owned WireGuard private key or replace root-owned network/firewall scripts. Current aggregate CPU, memory, and SirinVPN-interface counters come from read-only kernel files. Rate calculation retains only one bounded prior sample in process memory, rejects stale/reset deltas, and is exposed only through the authenticated private status endpoint.
- Normal production services have stdout and stderr directed to null. SirinVPN creates no activity log, connection history, DNS history, or audit database.
- Opt-in Linux full-tunnel protection installs an owned output guard before normal boot networking. Its bounded exceptions cover loopback, the active tunnel, DHCP, narrowly scoped IPv6 neighbor discovery, explicit LAN ranges and marked transport/endpoint-control/DNS traffic. Ordinary system DNS remains blocked off-tunnel. Selected-route protection guards its configured CIDRs and private/system DNS while intentionally allowing unrelated destinations. Linux application routing uses an explicit owned namespace and permanently unprivileged launched child; see [application routing](docs/linux-application-routing-2026-09-07.md).
- Linux kill switch, reconnect and startup are independent current policies. A root-private desired record can retain up to four authenticated transport candidates, exact endpoint descriptors, routing and MTU settings plus native WireGuard material. The supervisor observes current route/handshake state, respects pause and explicit disconnect, holds protection during route loss, and uses bounded recovery/backoff. Guard replacement is atomic and cleanup uncertainty fails closed. Quality/MTU probes use only the private server; voluntary optimization requires protected idle conditions and restores a working candidate on failure. Samples, route epochs and comparison state do not become activity history. Live helper downgrade requires disconnect and compatible state readers.
- On an IPv6-capable VPS, SirinVPN deterministically derives a private ULA `/64` from the random server UUID and maps the existing IPv4 host number into each device's `/128`. The privileged helper rejects any IPv6 address that does not match that server/device derivation. The VPS accepts only each peer's exact `/128`, forwards only the SirinVPN ULA, and uses NAT66 rather than pretending to delegate a public prefix.

Member lifecycle policy, bounded reusable invitations and delegation are documented in [authorization policy](docs/member-policies-and-invitations-2026-09-06.md). Offline administrator recovery requires the configured encrypted recovery material and pinned SSH/server-identity proof; it is not a public recovery endpoint. See [Owner recovery](docs/offline-owner-recovery-2026-09-06.md). Signed VPS updates retain independent trust/high-watermark state, compatible rollback and an explicitly enabled security-update timer with no default source; [the VPS update design](docs/signed-vps-updates-2026-09-06.md) defines that privilege boundary. Windows app updates reverify signed artifacts in an administrator-only coordinator.

## Threat boundary

The implemented foundation is intended to resist local network observation of payloads selected for tunneling, accidental system-DNS use outside the tunnel while connected, unauthenticated or revoked access to the private management API and VPN, invitation modification/replay, and unsafe installer/repair interruption. Selected-route and selected-application modes intentionally leave traffic outside their configured scope on the normal network, subject to the platform protection policy.

SirinVPN does not protect against:

- compromise of the client, the user's desktop session, root on the client, or root on the VPS;
- a malicious VPS provider or malicious destination;
- traffic analysis at the VPS or global-adversary correlation;
- blocking of the VPS IP, blocking every UDP/TCP fallback, fingerprinting an authenticated wrapper or the self-signed TLS endpoint despite padding and silent inner-probe behavior, or TCP-over-TCP performance collapse under loss;
- traffic leaks while disconnected from a transient session or after the user explicitly disables persistent protection;
- a malicious binary the user chose to install or authorize with polkit;
- denial of service, server seizure, or loss of all local key material.
- substitution of an entire invitation code through an untrusted sharing channel; recipients must receive the bearer code from a trusted person/channel.
- capture of a displayed QR or long code before redemption/expiry; either representation grants the same bounded invitation authority and must be treated like a password.
- disclosure of an encrypted device backup together with its password; that pair contains a complete authorized-device identity until the device is revoked on the VPS.
- disclosure of an encrypted server-state backup together with its password; that pair can clone the backed-up VPS identities and authorization, including access that may now be stale.
- continued operation of an old VPS identity clone after migration; signed endpoint distribution does not revoke, shut down, or erase that host, so the Owner must retire it separately after every device has moved.

On a capable VPS, the helper installs full-tunnel or selected routes and policy rules for both requested address families; on an IPv4-only VPS, full mode installs a temporary nftables IPv6 output block for transient sessions, while selected mode leaves unselected IPv6 outside the VPN and refuses IPv6 selections. Persistent protection keeps the matching full or scoped output guard active while reconnecting. If transient setup cannot apply every required address, route, rule, firewall, and DNS setting, the helper removes its owned state in both families and reports failure. If a persistent reconnect cannot rebuild the configured tunnel, it keeps the applicable guard and retries; selected policy intentionally continues to allow unselected traffic. NAT66 means tunneled IPv6 destinations observe a VPS IPv6 egress address rather than a unique delegated client address.

Persistent protection does not defend against root on the client. A root process can read the desired WireGuard key, alter nftables, stop the services, or mark its own endpoint traffic. The endpoint exception is restricted by both destination and WireGuard's privileged fwmark so an ordinary process cannot use it as a general bypass.

## SSH fingerprint procedure

The first connection can display a host fingerprint but cannot establish its authenticity by itself. Compare it with the fingerprint shown in the hosting provider console or retrieve it through another trusted administrative path. A host replacement requires a new explicit verification; pins are never silently updated.

## Release safety

Use the Debian container build for distributable Linux artifacts, retain both lockfiles, and run `./scripts/test.sh`. P1B5 deliberately uses only the local artifact packaged with the running client and performs no release lookup, but SHA-256 transport/integrity checks do not prove publisher provenance. The repository has a pre-distribution public bootstrap root but no published production trust anchor, signed release, or configured release source yet. Before distribution, place the matching root private key and its backup in encrypted offline custody (or replace the bootstrap root), create and verify the initial root-signed release-key policy, create the signed artifact bundle, exercise the HTTPS retrieval gate against its exact publication layout, initialize policy state and the installed receipt/cache only after successful first package installation, and run the isolated transactional Debian upgrade/rollback/recovery gate.

The historical [2026-09-04 overhaul audit](docs/audit-2026-09-04.md) records dependency results and application fixes for that checkpoint.
