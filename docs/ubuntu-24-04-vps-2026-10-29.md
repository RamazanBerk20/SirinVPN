# Ubuntu 24.04 LTS VPS support

The installer now accepts `ID=ubuntu`, `VERSION_ID=24.04` (every 24.04.x point
release) on `x86_64` and `aarch64`, alongside Debian 13. Other releases,
including Ubuntu 22.04 and 24.10, are still rejected before any change. The
install transaction is the same on both distributions; there is no
distribution-specific branch beyond these:

- The package step sets `NEEDRESTART_SUSPEND=1`. Ubuntu server images ship
  needrestart, whose apt hook otherwise restarts services that use upgraded
  libraries in the middle of the install. On Debian the variable has no effect.
- Network preflight detects UFW with `ufw status` instead of
  `systemctl is-active ufw`. Ubuntu's `ufw.service` is a oneshot that stays
  active while UFW itself is disabled, so the old check reported UFW on every
  Ubuntu host. An enabled UFW gets a non-blocking note. SirinVPN does not
  change UFW.

## Verified on 2026-10-29

### Disposable Ubuntu 24.04 VM

These runs used a local QEMU/KVM guest with 2 GiB of RAM and 2 vCPUs. No
VPS was used.

- **Image.** `ubuntu-24.04-server-cloudimg-amd64.img` from Ubuntu's
  `releases/noble/release-20261017`. `SHA256SUMS` carries a good signature
  from the Ubuntu cloud-image key `D2EB44626FDDC30B513D5BB71A5D6C4C7DB87C81`,
  and the image matches its SHA-256 (`04e8f246…985b6c94`). The guest reported
  Ubuntu 24.04.5 LTS with kernel 6.8.0-147-generic.
- **Payload.** The x86_64 server was built from commit 2171855 in
  `packaging/Dockerfile.server-payloads` (Bookworm). Its SHA-256 is
  `595ed263…cd847e50` and it needs at most `GLIBC_2.34`.
- **`tests/vm/debian13.sh` passed.** The checks it ran:
  - Installation.
  - All four SirinVPN services were active.
  - UDP and TCP 443 had listeners and matching nftables accept rules.
  - The install stayed IPv4-only, with no `sirinvpn_nat6`.
  - Repair after deleting the firewall unit kept every identity and
    authorization hash and installed the candidate artifact.
  - A conflicting reinstall rolled back to an identical `server.json`.
- **A second boot of the same image and payload recorded the following.**
  - **Installed packages.** The image already ships needrestart, UFW
    (inactive), systemd-resolved, AppArmor, unattended-upgrades and nftables.
    The installer added only wireguard-tools, unbound and dns-root-data, plus
    two library dependencies. It upgraded nothing.
  - **UFW detection.** Before installation, `systemctl is-active ufw` said
    `active` while `ufw status` said `inactive`. Preflight gave no UFW note.
    The only note was the expected `private_endpoint` for 127.0.0.1. After
    `ufw allow 22/tcp` and `ufw --force enable`, preflight reported the UFW
    note and the drop-policy note. Neither blocked installation.
  - **Services.** After installation, all of these were active:
    sirinvpn-network, sirinvpn-firewall, sirinvpn-server, unbound,
    systemd-resolved and unbound-resolvconf. No unit failed.
  - **DNS listeners.** Unbound listened on 127.0.0.1:53 and 10.77.0.1:53.
    systemd-resolved listened on `127.0.0.53%lo:53` and `127.0.0.54:53`.
  - **Host DNS.** `resolvectl` showed no loopback DNS entry, so the host kept
    its provider resolver. Host name resolution worked.
  - **AppArmor.** Unbound ran confined by its AppArmor profile in enforce
    mode.
  - **WireGuard.** The module loaded on the 6.8 kernel, and `sirinvpn0`
    listened on UDP 51820.
  - **Security-update timer.** `sirinvpn-security-update.timer` was
    installed but disabled, as it is opt-in. Both of its units passed
    `systemd-analyze verify` on the guest.
  - **Journal.** Ubuntu's unbound unit logged only a harmless warning about the
    unset `DAEMON_OPTS` variable.

### Two-VM client lab with an Ubuntu VPS

`tests/vm/run-linux-acceptance.sh` ran with a Debian 13 client guest (kernel
6.12.107+deb13-cloud-amd64) and an Ubuntu 24.04.5 VPS guest (kernel
6.8.0-147-generic) booted with `--vps-base`. The client installed
`SirinVPN_0.1.1_amd64.deb` (SHA-256 `9e5d1bff…5eea7ed6`), built by
`scripts/package-linux-container.sh` from commit 48ecbc6. That package's CLI
provisioned the VPS with its bundled server.

The VPS used a DNS-over-TLS upstream (`--vps-dns-over-tls
9.9.9.9#dns.quad9.net`). All 27 checks passed in 11.9 minutes, and guest
cleanup completed:

- Provisioning and enrollment through the packaged CLI, then the physical
  IPv4, IPv6 and leak-counter baselines.
- DNS attribution before protection and during forced transport fallback.
- Direct UDP, Obfuscated UDP, TLS and TCP. Each exited through the VPS with
  native DNS resolved from the VPS, the kill switch armed, zero physical DNS or
  IPv6 leak counters, and a clean disconnect.
- Public HTTPS through the tunnel (HTTP 200).
- Closing the real desktop window kept the tunnel.
- Stopping the VPS resolver kept the tunnel without DNS fallback, and the
  resolver recovered afterwards.
- Recovery from abrupt termination of the TLS transport process.
- All four kill-switch and reconnect combinations after a tunnel interruption.
- Automatic fallback with both UDP transports blocked.
- After power loss, protection stayed blocking and recovered through the VPS.
- Removing the client while connected restored physical networking.
- Uninstall over pinned SSH removed the VPS's SirinVPN files and firewall
  tables and preserved an unrelated nftables table.

An earlier run used the default recursive resolver. Everything up to and
including the desktop-window check passed, then public HTTPS failed because
`example.org` did not resolve. The cause is this workstation's network, which
intercepts all outbound UDP/53. Non-recursive queries to root servers, and even
to TEST-NET addresses such as 192.0.2.1 where no DNS server exists, came back
with recursive answers. So the VPS's unbound never got a root delegation. The
same interception reached a clean Debian 13 guest, so this is not an Ubuntu
difference.

### Workstation checks

- **Repository gate.** `./scripts/test.sh` passed, including the Rust
  workspace tests and 233 desktop tests.
- **Installer unit tests.** The compatibility gate accepts Debian 13 and
  Ubuntu 24.04 on both architectures and rejects other versions and
  architectures. An enabled UFW gives exactly one non-blocking note. The
  systemd-resolved stub listeners on 127.0.0.53 and 127.0.0.54 are not treated
  as conflicts with SirinVPN's DNS listener, with or without the `%lo` suffix.
- **Generated configuration.** Install scripts were generated for Recursive,
  DNS-over-TLS, DNS-over-HTTPS with IPv6, and split DNS. Each passed these
  checks in an `ubuntu:24.04` container:
  - `sh -n` with dash
  - `unbound-checkconf` 1.19.2
  - `nft -c` 1.0.9
  - `systemd-analyze verify` with systemd 255

  A Debian 13 container passed the same checks as a control.
- **needrestart.** In 3.6-7ubuntu4.5, `/usr/lib/needrestart/apt-pinvoke` exits
  without running needrestart when `NEEDRESTART_SUSPEND` is non-empty.
- **aarch64 payload.** A static ELF check passed: at most `GLIBC_2.34`,
  linking only libc, libm and libgcc_s. Ubuntu 24.04 has glibc 2.39.

## Not verified

- **Recursive public DNS on Ubuntu.** The VPS's default recursive resolver
  could not be exercised for public names behind this workstation's DNS
  interception. Only the private records and the DNS-over-TLS upstream were
  exercised.
- **MTU and port forwards.** Neither the lab nor the gate checks MTU behavior
  or port forwards.
- **Other server operations on Ubuntu.** These were not run:
  - server restore
  - applying a signed VPS update
  - the security-update timer performing an update
- **IPv6.** The VM was IPv4-only, so dual-stack installation on Ubuntu was not
  exercised.
- **aarch64.** The aarch64 payload was not run on any Ubuntu host.
- **Provider images.** Cloud-init customizations, preinstalled agents or
  firewalls on real Ubuntu VPS images were not covered.
- **Installing with UFW enabled.** Preflight reports an enabled UFW, but it
  does not determine which UFW rules the VPN needs. Expect the listed ports,
  tunnel DNS and management on `sirinvpn0`, and forwarded tunnel traffic to be
  dropped until matching rules are added.
- **needrestart at runtime.** The VM install upgraded no package, so
  needrestart had nothing to restart either way. Its suspension is verified
  only from the hook source.
- **dpkg lock after first boot.** On a fresh cloud VPS, unattended-upgrades
  can hold the dpkg lock. The dependency step then fails before any SirinVPN
  change and has to be retried. This did not occur in the VM runs, it is not
  mitigated, and it applies to Debian cloud images too.

## Reproducing the VM runs

```sh
SIRINVPN_DEBIAN13_IMAGE=/absolute/path/ubuntu-24.04-server-cloudimg-amd64.img \
SIRINVPN_TEST_SERVER_BINARY=/absolute/path/target/server-payloads/x86_64-unknown-linux-gnu/release/sirinvpn-server \
  sh tests/vm/debian13.sh
```

The two-VM client lab:

```sh
sh tests/vm/run-linux-acceptance.sh \
  --base /absolute/path/debian-13-genericcloud-amd64.qcow2 \
  --vps-base /absolute/path/ubuntu-24.04-server-cloudimg-amd64.img \
  --package /absolute/path/SirinVPN_0.1.1_amd64.deb \
  --output /absolute/path/new-output-directory
```

Add `--vps-dns-over-tls 9.9.9.9#dns.quad9.net` if the host network intercepts
outbound DNS.

Use a disposable VM or VPS, never a personal one.
